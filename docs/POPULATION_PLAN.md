# План: популяции стратегий в backtest venue

Документ фиксирует целевую архитектуру эволюции venue: обслуживание популяции
стратегий на общем стакане с оффсетами горизонтов и per-strategy impact-state,
затем multi-population через unix socket + SPSC и индекс датасетов.

> **Писать код по:** [`POPULATION_IMPL.md`](POPULATION_IMPL.md).

## 1. Исходные заметки

1. **Популяция в одной группе.** Venue берёт стакан и двигает его для каждой
   стратегии популяции. На популяцию — один shared snapshot / cursor; у стратегий —
   разные оффсеты горизонтов.
2. **Сдвиг по max-offset.** Стратегия с наибольшим оффсетом инициирует сдвиг ленты;
   более мелкие догоняют, пока разброс горизонтов не станет примерно ±1 горизонт;
   цикл повторяется.
3. **Per-strategy state.** После наших филлов объём на уровне восстанавливается
   экспоненциально, если в следующем снепшоте из файла эти ордера / объём всё ещё
   видны — иначе стратегии необратимо ломают общий файл-стакан.
4. **Мультикомпонентный датасет (канон).** На популяцию — до **трёх** книг:
   спот + фьючерс + опцион; меньше, если ноги нет. Не один JSONL. Текущий код
   ещё считает одну книгу — догнать в P1b.
5. **Много популяций (future).** У каждой — свой стакан + оффсеты. Одна пара
   CMF-портов не масштабируется: нужен уровень выше (UDS + пары SPSC; позже квоты).
6. **Много датасетов.** Нужен быстрый старт сессии: индекс (B-tree / аналог) по
   времени / инструменту.

### Допущение по транспорту

| Фаза | Транспорт |
| --- | --- |
| Phase 1 | Venue слушает **unix socket**; Trading Engine dial’ит и шлёт OpenPopulation |
| Hot path | При успехе (позже — при наличии **квоты**) venue поднимает **2×SPSC**: out = venue→engine (Tick/Ack/End), in = engine→venue (Orders/Advance/Close) |
| Phase 2 | Квоты, индекс датасетов, multi-population fairness |
| Совместимость | CMF TCP (`feed` + `orders`) остаётся single-session путём и smoke-тестом, **не** multiplex |
| Не делаем | **gRPC** (отдельный runtime, лишняя стоимость на горячем пути) |

## 2. Текущее состояние (якорь)

Сейчас (`src/venue/venue.cc`, `include/cmf/cmf_driver.hpp`):

- 1 процесс = 1 инструмент = 1 пара TCP = 1 «аккаунт» (`K`) = один `Working` book.
- Горизонт `H` / lookahead `Δ` — это **CMF sync** (Chandy–Misra–Bryant), не оффсет
  стратегии в популяции.
- Филл деструктивно уменьшает `bids_` / `asks_`; следующий JSONL-ивент перезаписывает
  стакан из файла — другая модель, чем нужна для популяций.
- Мультисимвол в протоколе есть (`class` / `sec`), в venue — фильтр на один `sec_code`.

```text
JSONL (один symbol) ──► Venue ── feed TCP (S/I/H/E) ──► Engine
                         ▲
                         └── order TCP (HELLO/N/C/TIME) ─┘
```

## 3. Целевая модель данных

Краткие определения — в [`GLOSSARY.md`](GLOSSARY.md). Здесь — семантика и правила.

### Предварительно: что значат времена

| Обозначение | Что это |
| --- | --- |
| **`T_pop`** (он же **`head_ts`**) | Общие «часы» популяции: логическое время (`ts_ns` из датасета) **последнего** события файла, которое уже прочитали и применили к **общему** стакану. Пока никто не сдвинул ленту — это время старта / последнего shared snapshot. |
| **`virtual_ts_i`** | Личные «часы» стратегии `i`: до какого момента она уже **обработана** (получила view, могла слать ордера). Может отставать от `T_pop`. |
| **`offset_i`** | Насколько стратегия позади головы: `T_pop − virtual_ts_i` (в наносекундах). Больше оффсет → сильнее отстаёт. |
| **`H_unit`** | Допуск «почти вместе» между слотами популяции (catch-up). Не путать с горизонтом стратегии ниже. |
| **`Δ` (delay)** | Задержка видимости ордера venue’ом / матчером: решение в `t_seen`, исполнение не раньше `t_seen + Δ`. Близко по смыслу к CMF lookahead из `HELLO`. |
| **`H_strat` (горизонт стратегии)** | Насколько вперёд по ленте стратегия «смотрит» / до какого момента её окно исполнения тянется от точки решения. |
| **Шаг ленты** | Гранулярность датасета (например 1 ms между обновлениями стакана). Исполнение идёт **по шагам ленты**, без прыжка через интервал. |

Не путать: `T_pop` — не сообщение CMF `H|ts`. `H_strat` / `H_unit` — не CMF horizon-promise. `Δ` — задержка ордера, не оффсет слота.

### 3.1 Последовательное исполнение (delay → горизонт)Где лежит один общий стакан из файла?

Исполнение **последовательное** вдоль датасета, а не одним скачком на конец окна.

Пример: обновления в датасете каждые **1 ms**, у стратегии горизонт **`H_strat = 10 ms`**, задержка видимости ордеров **`Δ = 4 ms`**. Решение в момент `t`:

1. До `t + 4` ордер ещё **не виден** матчеру (летит / не вступил в силу).
2. Начиная с `t + 4` ордер можно исполнять против стакана.
3. Дальше идём по ленте шагом датасета **до `t + 10`**:  
   `4 → 5`, `5 → 6`, …, `9 → 10` (мс относительно `t`).
4. На каждом шаге: применить file snapshot этого ms → recovery impact слота →
   матч resting / нового ордера против **effective** book слота.

```text
t          t+Δ=t+4              t+H_strat=t+10
│          │                    │
│  delay   │  sequential match  │
│  (ждём)  │  4→5→6→…→10 (1ms)  │
└──────────┴────────────────────┘
```

Итого в этом примере матчинг живёт на интервале **`[t+Δ, t+H_strat]`**, дискретизация =
шаг датасета. Если `H_strat ≤ Δ`, исполнять нечего (окно пустое) — такую конфигурацию
отклонять или трактовать явно.

Тот же принцип для продвижения cursor’а популяции: лидер/догоняющие двигают ленту
**последовательными** событиями/шагами, а не прыжком на `H_unit` вперёд.

### 3.2 Как устроен стриминг (канал стратегии)

**Логическая картина (то, что видит стратегия):** у каждой стратегии **один** канал
(один поток market+orders для слота). По этому каналу ей двигают **сразу все
компоненты bundle** — спот, фьюч, опцион (сколько есть в манифесте) — **на её
горизонт**, одним шагом времени.

Не три канала «отдельно спот / отдельно фьюч / отдельно опцион» и не «сначала
весь спот, потом фьюч». Один тик стрима ≈ «время стало `T`, вот актуальные
стаканы всех ролей на `T` (или diff с прошлого тика) + можно отвечать ордерами».

```text
канал слота A                          канал слота B
─────────────                          ─────────────
T=100: spot+fut+opt books              T=100: spot+fut+opt books
  ← orders A                             ← orders B
T=101: spot+fut+opt (шаг 1ms)          … (B ещё на 100, догоняет позже)
T=102: …
… до virtual_ts_A += H_strat …
```

**Как стакан «догоняется»:** если слот отстаёт (`virtual_ts` меньше `T_pop`), по
его каналу подряд льются шаги ленты `virtual_ts → virtual_ts+step → …`, пока он
не окажется в пределах `H_unit` от головы (или не получит свой квант горизонта).
На каждом шаге обновляются **все** компоненты, у которых на этом `ts` есть
событие; роли без события на этом ms сохраняют прошлый стакан. Effective book
слота = file snapshot на этом шаге минус его impact; чужие слоты в канал не
попадают.

**Физическая картинка (внутри venue, для ясности):** файлы спот/фьюч/опцион
читаются **один раз** на популяцию (`SharedCursor` + merge). Scheduler выбирает,
кому сейчас слать следующий шаг (лидер по offset, потом catch-up). В транспорт
это уходит как сообщения с `slot_id` — логически «канал на стратегию», на проводе
можно мультиплексить в один bidi stream популяции. Ордера обратно тоже с
`slot_id`, матч только в state этого слота.

Итого одной фразой: **один канал = одна стратегия; по каналу двигаются сразу все
инструменты bundle на горизонт этой стратегии; догон = последовательные тики по
её каналу, пока не сравняется с популяцией в пределах `H_unit`.**

### 3.3 Shared cursor + оффсеты

- У популяции база `T_pop` / `head_ts` — см. таблицу выше.
- У слота `i`: `offset_i := T_pop - virtual_ts_i` (отставание от головы).
- Вид рынка для слота — проекция shared (file) book на момент слота **плюс** его
  `ImpactState`.
- **Правило продвижения:** `leader = argmax(offset)` (самый отстающий; при равенстве —
  меньший `slot_id`). Cursor двигается под лидера; остальные догоняют, пока
  `max(offset) - min(offset) ≤ H_unit`. Затем следующий round.

В классическом PDES двигают min virtual time. Если оффсет = «насколько позади головы»,
то `argmax(offset) ≡ argmin(virtual_ts)` — согласовано с заметками. Эту семантику
нужно зафиксировать в коде явно (см. формулы в глоссарии).

```text
PopulationScheduler
  │
  ├─► Slot_maxOffset ── shift SharedCursor ── new snapshot
  │
  └─► Slot_smallOffset ── catch up within H_unit
        (когда spread ≈ один горизонт — следующий round)
```

### 3.4 Изоляция стратегий внутри популяции

**Инвариант:** стратегии в одной популяции **не конкурируют** за книгу и **не видят**
ордера / филлы друг друга. У каждой по сути свой стакан (свой effective book + свои
resting orders). Общее только чтение ленты: один `SharedCursor` / file snapshot на
популяцию (экономия памяти и I/O), а не общий торговый аккаунт.

Следствия:

- филл стратегии A не уменьшает ликвидность, которую видит B;
- resting DAY-ордера A не стоят в книге B и не матчятся с B;
- оценка генома независима от состава популяции (при том же датасете и seed’е
  scheduler’а).

### 3.5 Per-strategy state и экспоненциальное восстановление

Файл-снепшот — рынок **без нас**. Филлы стратегии вычитают объём **только в её**
effective book. Мутация одного общего мутабельного book скрещивала бы стратегии и
ломала калибровку геномов — этого не делаем.

Модель (логически свой стакан на слот, физически без полного clone):

1. **Shared file book** = как в файле (после merge компонент), read-only база, без
   наших ордеров.
2. **ImpactState[slot][instrument][side][px]** = `eaten_qty` + `t_last` — локальное
   «проедание» ликвидности слотом.
3. **Effective qty** для слота = `max(0, file_qty - eaten_qty_слота)`.
4. **Recovery:** при новом снепшоте / тике, если уровень в файле жив:
   `eaten *= exp(-λ · Δt)`. Если уровень исчез — сбросить eaten.
5. Филл слота увеличивает **только** его `eaten`. Resting DAY — только в его
   `Working`.

Полный clone book на стратегию — допустим для отладки малых N, но не default:
память `O(strategies × levels × components)`. Default — file book + sparse impact.

«Ордера восстанавливаются по экспоненте» ≈ восстановление **объёма уровня** в
effective book слота, не re-insert чужих / наших working orders в shared file book.

### 3.6 ComponentBundle (spot / fut / opt)

Для популяции ленту двигают **не один**, а **несколько датасетов сразу** — обычно
три: **спот**, **фьючерс**, **опцион**. Один shared `T_pop` / merged clock на все
компоненты: сдвиг под лидера и последовательное исполнение (`Δ → H_strat`) идут по
**общей** шкале времени, обновляя те книги, у которых на этом шаге есть событие.

Если каких-то данных нет (нет спота, или только опцион и фьюч, или один инструмент) —
в bundle меньше компонент, движок просто двигает то, что есть. Пустые роли не
создаём и не ждём.

Один DatasetHandle = манифест:

- `bundle_id`
- компоненты `{ role, path, class, sec, tick }` — `role ∈ { spot, future, option, … }`,
  список **1…N** (типично до 3)
- выравнивание по `ts_ns`

Scheduler читает **merged timeline** (min-heap по ts курсоров компонент) и выдаёт
`MarketTick { ts, role, event }`. Слот видит **столько** стаканов, сколько компонент
в bundle, на одном `T_i`.

```text
Population SharedCursor
  ├─ spot.jsonl     ──┐
  ├─ future.jsonl   ──┼─ merge by ts_ns ──► MarketTick → все слоты (свой effective)
  └─ option.jsonl   ──┘   (отсутствующие роли просто не в манифесте)
```

Проще, чем три независимые CMF-сессии: один logical clock на bundle.

- CMF single-engine путь: можно публиковать несколько `sec` в одном feed.
- In-process популяция: несколько `BookView` в слоте без TCP.

## 4. Транспорт: Unix socket + SPSC

### 4.1 Почему одна CMF-сессия не тянет

CMF жёстко: 1 venue process ↔ 1 engine, два TCP, один `HELLO` / `Δ`, один origin
`K`. В framing нет session / population id — мультиплекс популяций не влезает.

### 4.2 Целевой слой (канон = ТЗ §5)

```text
Unix socket  (весь прогон)
  create 2×SPSC | reject
  SessionEnded { ok | fatal }     # и норма, и критика — сюда
        │
        ▼
2× SPSC — протокол тиков
  out: OpenAck / Tick / OrdersAck / End / Error   # Error/End = hot path
  in:  Open / OrderBatch / Advance / Close
        │
        ▼
PopulationScheduler ── SharedCursor + Index
                   └── StrategySlots (state)
```

- Логика тиков та же; носитель = очереди, не gRPC.
- UDS = create + финальный `SessionEnded` (гарантия, даже если SPSC полна).
- Fatal: Error в SPSC → SessionEnded(краткий диагноз) → ждать **Close**
  (стратегия прочитала); нет Close за timeout → аварийный teardown сами.
- Recoverable `OrdersAck` — позже.
- CMF TCP — адаптер «1 population, 1 slot» / smoke.

### 4.3 Много популяций

- Изоляция: свой SharedCursor, ImpactStates, bundle (или shared read-only mmap
  датасета + свой cursor); своя пара SPSC.
- Параллелизм: thread / pool per population.
- Не шарить мутабельный book между популяциями.
- Fairness: quantum’ы на популяцию; квота ограничивает число одновременных Open.

## 5. Индекс датасетов

Цель: старт сессии с `ts_start` без полного скана JSONL с нуля.

### Практичный минимум

1. При конвертации (или отдельным indexer) писать sidecar:
   - `manifest.toml` — компоненты, tick, class / sec;
   - `index.bin` — массив `(ts_ns, file_offset)` каждые N событий + keyframe offsets
     для полных snapshot.
2. Старт сессии: binary search / `lower_bound` по `ts` → `seek` в файл / mmap.
3. B-tree / LSM — на **каталоге** датасетов (`symbol × day → файл`), не обязательно
   внутри одного JSONL. Для одного дня **vector + lower_bound** достаточно.

JSONL для горячего пути тяжёлый; medium-term — бинарные снепшоты. Phase 1 не
блокировать сменой формата — только sidecar index.

## 7. Замечания и риски

1. **Имя «горизонт».** В репо занято CMF `H`. В коде / доках популяции —
   `HorizonOffset` / `H_unit`, явно отличать от `AnnounceHorizon`.
2. **Детерминизм.** При равных offset порядок catch-up стабилен по `slot_id`,
   иначе генетика несравнима между прогонами.
3. **Изоляция внутри популяции (жёсткое требование).** Свой effective book на слот:
   нет конкуренции за ликвидность, нет видимости чужих ордеров/филлов. Общий только
   file cursor. Режим «один ImpactState на популяцию» — другая экономика, **не** в
   скоупе.
4. **CMF increments.** Engine может игнорировать `I` ([TASK.md](TASK.md) §5.2).
   Внешнему engine — слать `S`; внутри популяции — нативные структуры.
5. **Apply order.** Сначала file book, потом вычесть recovered eaten. Иначе
   экспонента бессмысленна при текущей перезаписи `bids_ = event.bids`.
6. **`λ`** — гиперпараметр в config популяции, не хардкод.
7. **Три компоненты ≠ три Δ.** Один lookahead на слот. Различия latency
   fut / spot / opt — stagger в merge, не разные HELLO.
8. **SPSC pair:** два однонаправленных кольца; не gRPC и не unary RPC на тик.
9. **Backpressure.** Cursor не убегает от самого медленного слота вне `H_unit` —
   это инвариант catch-up.
10. **Память.** Cursor / index read-only shared; дорогое — ImpactState и resting
    orders. Бюджет: top-N levels, GC нулевых eaten.

---

## 8. Идеи упростить

- Не копировать стакан на слот: file book + sparse impact map.
- Вместо B-tree сразу — `lower_bound` по sorted ts-index; B-tree только для
  global catalog.
- Схема сообщений (можно из `protos/`) без gRPC runtime — фрейминг в UDS/SPSC.
- Популяции — независимые задачи на thread pool.
- CMF остаётся regression-путём на 1 slot.

### Рекомендуемый порядок работ

1. Зафиксировать глоссарий и формулы (`GLOSSARY.md` — уже черновик).
2. P0 — `PopulationScheduler` на одном JSONL.
3. P1 — impact + recovery; не ломать CMF smoke.
4. P1b — bundle из нескольких компонент.
5. Sidecar index + seek.
6. P2 — UDS control + SPSC pairs на много популяций; квоты.

## 11. Вне скоупа этого плана

- Смена CMF line-protocol на что-то другое для single-engine пути.
- Калибровка конкретного `λ` под прод-данные.
- Полная замена JSONL на колонный / бинарный формат горячего пути (только
  отмечено как medium-term).
- Global B-tree catalog по всем датасетам (после sidecar index на один файл).

## 12. Пометка на будущее (не в скоупе P0–P1)

**Tape stride / сжатие истории для ускорения бэктеста.**  
Сейчас канон UDS+SPSC — **последовательный цикл каждого тика** (view → orders →
fills → Advance). Позже: сжать ленту 1 ms → N ms для более быстрых прогонов;
каждый страйд всё равно с round-trip (не немой прыжок). `md_lag` / `Δ` в тех же
единицах. Точность vs скорость — отдельный рычаг, когда дойдём до perf.
